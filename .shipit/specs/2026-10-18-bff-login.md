# BFF email/password login (feature 1)

Status: complete (2026-10-18). All acceptance criteria verified, including the
token-refresh survival check.

## What

Email/password login through the BFF. The gateway runs the authorization code +
PKCE flow against Keycloak, stores the session (SecurityContext and authorized
client with tokens) in Redis, and issues an HttpOnly SameSite session cookie.
The browser only ever holds that cookie and the XSRF cookie.

Pieces:

- Gateway: OIDC client (code + PKCE), `@EnableRedisWebSession`, session cookie
  `SESSION` (HttpOnly, SameSite=Lax), TokenRelay to the API, RP-initiated
  logout, back-channel logout endpoint, CSRF cookie to header for Axios.
- `/bff/user` through the gateway to the API's protected profile endpoint; the
  request carries no bearer token, the gateway relays it.
- API: JWT resource server (issuer-uri) with a profile endpoint.
- Web: React page showing the logged-in user, Sign in / Sign out, Axios with
  credentials and automatic X-XSRF-TOKEN header.

## Acceptance criteria (from PRODUCT.md first result, minus registration)

1. Login with email/password starts a gateway session and sets a session cookie.
2. `GET /bff/user` through the gateway returns the user's profile data. No
   bearer token in the browser request; the gateway relays the token to the API.
3. Logout ends the session and clears the cookie (RP-initiated logout).
4. With no valid session, `/bff/user` is rejected.

Extra verification for this step (from the request):

5. The session key appears in Redis (`spring:session:sessions:*`).
6. No OAuth token is visible in browser storage or JS (localStorage,
   sessionStorage, `document.cookie` shows only the XSRF cookie; the SESSION
   cookie is HttpOnly and invisible to JS).
7. A second gateway instance can serve the same session (session and authorized
   client live in Redis, not in memory).

## How to check

- `.\gradlew.bat build` for Java, `npm run build` in /web.
- docker compose infra up, run gateway (8181) and api (8182), web dev on 5174.
- Browser: sign in as alice, see profile on the React page, sign out.
- `redis-cli` for the session key; browser devtools evaluate for storage check.
- Start gateway 2 on 8191, call `/bff/user` on 8191 with the same cookie jar.

## Notes

- Login endpoints keep Spring Security defaults (`/oauth2/authorization/gateway`,
  `/login/oauth2/code/gateway`, `/logout`); the Vite dev proxy forwards those
  paths (plus `/bff`) to the gateway so the browser sees one origin. This
  adjusts the earlier "proxies /api and /auth" note in PRODUCT.md, which
  predates this feature.
- Back-channel logout OIDC session registry stays in memory (one instance at a
  time in dev), as recorded in PRODUCT.md.
- SPA and XHR: unauthenticated calls must get 401 (never a login redirect),
  because XHR cannot follow the cross-origin redirect chain to Keycloak
  (CORS preflight). Same for logout: `POST /logout` (CSRF) answers with the
  RP-initiated logout URL as JSON and the SPA opens it as a top-level
  navigation.
- Keycloak realm: `post.logout.redirect.uris` must be whitespace-separated or
  the special value `+` (reuse the redirect URIs). The original comma list was
  read as one URI and failed with "Invalid redirect uri". Fixed in
  `infra/playground-realm.json` and on the live realm.
- Keycloak enforces PKCE S256 for the gateway client; Spring Security only
  adds PKCE automatically for public clients, so the gateway applies
  `OAuth2AuthorizationRequestCustomizers.withPkce()` on the authorization
  request resolver.
- Session id rotation bug (found and fixed): `DefaultReactiveOAuth2AuthorizedClientManager`
  runs `RefreshOidcUserReactiveOAuth2AuthorizationSuccessHandler` on a token
  refresh, which re-reads the ID token and saves the updated user through its
  own `WebSessionServerSecurityContextRepository`. That repository changes the
  session id on every save (session fixation), so a refresh rotated the id and
  a parallel request on the old id saw an empty session and expired the cookie,
  logging the browser out. (Spring Security main already guards this with a
  non-rotating repository; 7.1.1 does not.) Fix: `StableSessionSecurityContextRepository`
  changes the id only when the signed-in principal changes (login), used both
  as the chain's repository and in the refresh success handler. The SPA also
  shares one in-flight user load so StrictMode does not fire parallel requests.
